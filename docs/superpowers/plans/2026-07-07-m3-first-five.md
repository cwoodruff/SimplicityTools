## Task 1 (inline): #90 Discoverability methodology

**Decision:** `TwoAmTestEvaluator` Discoverability becomes `InverseThreshold(PrimaryPathFileCount / max(1, TotalProjects), 5.0)` — “five primary-path files *per project* to trace a flow at 2 AM.” Rationale: flow tracing happens within a project boundary; an absolute 5-file cap penalizes exactly the concentration PrimaryPathFirst rewards, making the two filters mathematically incompatible above ~8 files. Per-project normalization lets a well-factored solution of any size satisfy both. Document in `docs/using-the-simplicity-tools.md` (methodology note) and update violation message copy.

**Files:** `src/SimplicityTools.Filters/TwoAmTestEvaluator.cs`, `tests/SimplicityTools.Filters.Tests/FilterEvaluationTests.cs`, docs.

## Task 2 (inline): #94 One scoring module

**Decision:** new `src/SimplicityTools.Filters/SimplicityScoring.cs` (public): `CalculateScore(snapshot, thresholds)` (the current `ReportGenerator.CalculateSimplicityScore` formula, but penalties normalized against configured thresholds instead of magic 0.8/3/etc.) and `GetComplexityBand(value, thresholds)` / `GetOnboardingBand(...)` returning (label, css-class) bands derived from thresholds (Excellent ≤ 0.6×target, Good ≤ target, Moderate ≤ 2×target, High above). `ReportGenerator` deletes its private formula + hardcoded bands and consumes the module with the already-threaded thresholds; `ComplexityBudgetReportBuilder` unchanged semantics (already threshold-based). Tests: same simplicity.json produces consistent verdict direction in budget text and report HTML (e.g. maxMethodComplexity 1.0 → terminal OVER BUDGET **and** HTML band not “Good”).

**Files:** `src/SimplicityTools.Filters/SimplicityScoring.cs` (new), `src/SimplicityTools.Cli/ReportGenerator.cs` (`CalculateSimplicityScore` at ~858, bands at ~497-510), tests in Filters.Tests + Cli.Tests.
